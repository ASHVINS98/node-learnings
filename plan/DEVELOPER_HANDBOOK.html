Part 1 — What a backend actually is

1. Client and server

Software that people use is almost always split in two halves.

The client is the part running on the user's device — a web page in a browser, a mobile app. It draws buttons and text. It is untrusted: anyone can open developer tools and change what it does.

The server (the "backend") runs on a computer you control. It holds the real data, enforces the rules, and answers questions from clients. This project — dv-service — is a server. It has no user interface at all. Its entire job is to answer requests.

Think of a restaurant. The client is the customer reading a menu and asking for things. The server is the kitchen: it holds the ingredients, decides what's actually available, and refuses to serve you something that isn't on the menu no matter how nicely you ask.

That last part is the key idea and it comes up constantly in this codebase. Rules must be enforced on the server, because the client can lie. You will find comments in this repo saying exactly that — for example, in SubmissionReviewsController.ts, the fraud gate is checked server-side with the note that the workstream is pointless "if a client can route around the Forensics page by calling this endpoint directly."

2. HTTP: the request and the response

Clients and servers talk over HTTP. Every exchange is one request and one response.

A request has four parts

PartWhat it isExample
MethodThe verb — what kind of actionGET, POST, PATCH, DELETE
PathWhich resource/v1/programs/abc-123/submissions
HeadersMetadata — who you are, what format you wantAuthorization: Bearer <token>
BodyThe data you're sending (not used by GET){ "outcome": "fraud_detected" }

The methods have conventional meanings, and this codebase follows them:

  • GET — read something. Must not change anything. You can call it a hundred times safely.
  • POST — create something, or perform an action.
  • PATCH — partially update something that exists.
  • PUT — replace something wholesale.
  • DELETE — remove something.
Why "GET must not change anything" matters. In this codebase you'll find FraudCheckService.listUnchecked carries the comment "Read-only: browsing the queue must not claim anything, or a reviewer scrolling a list would lock every file they looked at." That's this rule, enforced in the domain.

A response has three parts

A status code (a number saying how it went), headers, and a body (the data).

CodeNameMeans
200OKIt worked. Data is in the body.
201CreatedIt worked and made something new.
400Bad RequestYou sent something malformed. Your fault.
401UnauthorizedWe don't know who you are. Log in.
403ForbiddenWe know who you are; you're not allowed.
404Not FoundNo such thing.
409ConflictValid request, but it clashes with current state.
429Too Many RequestsYou're going too fast (rate limited).
500Internal Server ErrorWe broke. Our fault.

The 4xx/5xx split is worth internalising: 4xx means the caller did something wrong, 5xx means the server did. Choosing correctly is how a frontend developer knows whether to fix their code or file a bug against you.

409 is used heavily in this project and is worth understanding. When two reviewers try to claim the same file, the loser gets a 409 — the request was well-formed, the caller is allowed, but the world moved. See SubmissionFraudChecksController.claimFraudCheck, where the comment reads: "A lost race is a 409, not a 500."

3. What an API is

An API (Application Programming Interface) is the set of requests a server agrees to answer. It's a contract: "send me this shape, I'll send you back that shape."

This project exposes a REST API, which is a style, not a technology. Its central idea is that URLs name things (nouns) and methods name actions (verbs):

GET    /v1/programs/:program_id/submissions        → list submissions
GET    /v1/programs/:program_id/submissions/:id    → read one submission
POST   /v1/programs/:program_id/settings           → create settings
PATCH  /v1/programs/:program_id/settings           → update settings

The :program_id part is a path parameter — a placeholder filled in with a real value. There are also query parameters after a ?, used for options that don't identify the resource:

GET /v1/programs/abc/submissions?pageNo=2&pageLimit=50&mode=inconclusive

The v1 is versioning. Once clients depend on your API, you can't change its shape without breaking them, so a new incompatible version lives at v2 while v1 keeps working.

This is why "additive changes" are safe and "changed meanings" are not. Adding an optional field to a response breaks nobody — old clients ignore it. Removing a field, or changing what an existing field means, breaks everyone. You'll see this reasoning in the codebase: an optional field was added to a response type specifically "so a client that predates them keeps parsing this branch unchanged."

4. What a database is

The server needs to remember things between requests. That's the database. This project uses PostgreSQL, a relational database.

Relational means data lives in tables — like spreadsheets. A table has named columns (each with a type: text, number, date, true/false) and any number of rows.

submissions
┌──────────┬─────────────┬────────────┬─────────────────────┐
│ id       │ program_id  │ status     │ created_at          │
├──────────┼─────────────┼────────────┼─────────────────────┤
│ 3fc72e4a │ 3f391910    │ in_review  │ 2026-08-11 21:18:03 │
│ 24972a60 │ 3f391910    │ approved   │ 2026-08-11 21:18:34 │
└──────────┴─────────────┴────────────┴─────────────────────┘

Keys and relationships

Every row needs a unique identifier — the primary key. This project uses UUIDs (those long 3fc72e4a-4603-... strings) rather than counting numbers, because UUIDs can be generated anywhere without coordination and don't leak how many records you have.

A foreign key is a column pointing at another table's primary key. That's the "relational" part. submissions.program_id points at programs.id, which is how the database knows a submission belongs to a program.

Foreign keys can carry rules. In src/db/schema/submissionFileFraudChecks.ts:

submission_id: uuid('submission_id')
    .notNull()
    .references(() => submissions.id, { onDelete: 'cascade' })

onDelete: 'cascade' means "if the submission is deleted, delete this row too." The alternative, set null, blanks the reference instead. Choosing between them is a real design decision about what should survive what.

Indexes

Finding a row by scanning every row is slow once you have millions. An index is a lookup structure the database maintains so it can jump straight to matching rows — like the index at the back of a book.

Indexes cost you: every write has to update them. So you add them deliberately, for queries you actually run. This codebase does exactly that, and even documents the query an index was built for:

index('idx_fraud_checks_live_claim')
    .on(table.submission_file_id)
    .where(sql`${table.outcome} IS NULL AND ${table.superseded_at} IS NULL`)

That's a partial index — it only indexes rows matching the WHERE, keeping it small and fast.

Constraints

A constraint is a rule the database itself enforces, so bad data physically cannot be written even if application code has a bug. The most important kind here is the unique index:

uniqueIndex('submission_file_fraud_checks_one_live_per_file')
    .on(table.submission_file_id)
    .where(sql`${table.superseded_at} IS NULL`)

This says: at most one non-superseded fraud check per file, ever. The comment above it explains the philosophy — "'Exactly once per file' is a DATABASE invariant, not application logic."

Learn this instinct early. If two users can do something at the same moment, application-level checks ("look first, then write") are not enough — both can look, both can see nothing, both can write. A unique constraint makes the database arbitrate, and exactly one wins. This is called a race condition, and constraints are the standard cure.

SQL and the ORM

SQL is the language for talking to the database:

SELECT * FROM submissions WHERE program_id = 'abc' ORDER BY created_at DESC;

Writing SQL as raw strings in application code is error-prone — typos aren't caught until runtime, and building queries by string concatenation opens SQL injection, where user input becomes executable SQL.

An ORM (Object-Relational Mapper) lets you express queries in TypeScript instead, with the compiler checking column names and types. This project uses Drizzle. You define the table once and get types for free:

export type ProgramSetting = InferSelectModel<typeof programSettings>;

Now if you rename a column, every place that reads it fails to compile — you find out immediately rather than in production.

5. Transactions: all or nothing

Some operations need several writes that must all happen or none happen. The classic example is a bank transfer: subtract from A, add to B. If the server crashes between them, money vanishes.

A transaction groups writes so they commit together or roll back together. Nothing in between is ever visible to anyone else.

await this.transactionService.executeInTransaction(async (tx) => {
    const claim = await this.fraudCheckRepo.claim(data, tx);
    await this.scheduleClaimTimeout(claim, tx);
});

Both writes take the same tx handle, so they're one unit. This exact code is in FraudCheckService.claimForCheck, and the comment says why: "a committed claim with a lost timeout is the exact failure this worker exists to prevent."

You'll see tx?: DrizzleTransaction as an optional last parameter throughout the repos. That's the pattern: if the caller is already in a transaction, join it; otherwise open your own.

6. Doing work later: queues and events

Some work shouldn't happen while the caller waits. If uploading a file also meant analysing the image, checking it against every other file, and calling three external services, the upload request would take thirty seconds and time out.

The fix is to do the fast part now, record that the slow part is needed, and answer immediately. Something else picks the work up.

The mechanism is a message queue — this project uses RabbitMQ. Terms you need:

TermMeaning
EventA record that something happened. Past tense, factual: SUBMISSION_FILE_DATA_SYNCED.
PublishAnnounce an event.
QueueA named line where messages wait.
ExchangeThe router that decides which queues get a copy of a message.
ConsumerCode that takes messages off a queue and acts on them.
Routing keyA label on the message the exchange matches against.

The important property is decoupling. The code that publishes doesn't know or care who listens. You can add a second listener without touching the publisher. In this project, SUBMISSION_FILE_DATA_SYNCED has two independent listeners — the fraud verdict worker and the security flags worker — and the comment in fraud-verdict-worker.consumer.ts explains the reasoning: "split transport by compute profile, not by policy," so a heavy analyser can't slow a light one.

Delivery guarantees

Networks fail mid-delivery, so systems choose between:

  • At-most-once — never duplicated, might be lost.
  • At-least-once — never lost, might be duplicated.

This project chooses at-least-once. That means your consumer might run twice on the same message, so handlers must be idempotent — running twice has the same effect as running once. This is not optional; it's a correctness requirement for every consumer you write.

7. Caching

A cache is a fast, temporary copy of data that's expensive to fetch. This project uses Redis, an in-memory store.

The pattern is cache-aside: look in the cache; if it's there (a hit), use it; if not (a miss), read the database, then store the result for next time.

The hard part is invalidation — throwing away cached data when the real data changes. Get it wrong and users see stale information. The repository base class in this project handles invalidation automatically when records change; see docs/data-layer/caching/.

Redis is also used here for rate limiting (counting requests per caller across multiple server instances), via rate-limit-redis.

8. Dependency injection

This is the concept most likely to feel strange, so here it is slowly.

A service usually needs other things to do its job. FraudCheckService needs a repository, a logger, a transaction service. The naive approach is to build them itself:

class FraudCheckService {
    private repo = new SubmissionFileFraudCheckRepo();   // ← builds its own
}

Three problems. It's now impossible to test without a real database. Everyone who needs a repo makes their own copy. And if the repo's constructor changes, every one of these lines breaks.

Dependency injection inverts it: the class declares what it needs and something else supplies it.

@Service()
@injectable()
export class FraudCheckService {
    constructor(
        @inject(SubmissionFileFraudCheckRepo)
        private fraudCheckRepo: SubmissionFileFraudCheckRepo,
        @inject(LoggerService) private logger: LoggerService
    ) {}
}

The "something else" is the container — here, TSyringe (src/container.ts). It knows how to build every registered class and wires the graph for you.

Two payoffs:

  1. Testing. Hand it a fake repo and you can test the service with no database at all. That's precisely what __tests__/unit/services/appServices/FraudCheckService.test.ts does — mockFraudCheckRepo.getLiveCheckForFile.mockResolvedValue(...).
  2. Singletons. One database connection pool shared by everything, rather than each class opening its own.

A chef who declares "I need a knife and a pan" and is handed them, versus a chef who forges their own knife every time they cook. The first can be given a plastic training knife for a rehearsal.

10. The layer cake

This is the single most important structural idea in the codebase. Every request travels down through the same four layers, and each layer may only talk to the one directly below it.

┌──────────────────────────────────────────────────────┐ │ CONTROLLER HTTP in, HTTP out │ │ parse params, validate body, pick │ │ a status code. No business rules. │ ├──────────────────────────────────────────────────────┤ │ SERVICE Business logic. Decides what should │ │ happen. Owns transactions. Knows │ │ nothing about HTTP. │ ├──────────────────────────────────────────────────────┤ │ REPOSITORY Data access. Builds queries. Knows │ │ nothing about business rules. │ ├──────────────────────────────────────────────────────┤ │ DATABASE PostgreSQL │ └──────────────────────────────────────────────────────┘

Why bother

Because each layer becomes testable and replaceable on its own. A service with no HTTP knowledge can be tested by calling a method — no server, no network. A repository with no business rules can be reused by three different services without any of them inheriting the others' assumptions.

The rule of thumb for "where does my code go?"

If the code…It belongs in…
reads req.params, req.body, or picks a status codeController
decides whether something is allowed, or orchestrates several stepsService
builds a query or touches a tableRepository
must be true no matter what code runs (uniqueness, referential integrity)Database constraint
The most common beginner mistake is putting business logic in the controller because it's convenient. The test is: could a background worker need this same rule? If yes, it belongs in a service, because a worker has no req object. This project has real examples — the fraud gate is checked in the controller, but the decision lives in FraudCheckService.evaluateGate, so both HTTP entry points and any future caller share one implementation.

12. How the app starts

Read src/index.ts top to bottom — it's the clearest map of the system. The order is deliberate, because each phase depends on the last.

1. reflect-metadata + dotenv load decorator support, read .env 2. ConfigurationManager fetch AWS secrets, validate all config with Zod 3. LoggerService now that config exists, real logging starts 4. Infrastructure, each optional: ├── PostgreSQL (DrizzleInstance.connect) ├── Redis (RedisInstance.connect) └── RabbitMQ (StartupRabbitMQManager) 5. Resolve App from the container dependencies find live connections 6. app.start() ├── JWTService.initialize ├── database init ├── RabbitMQ services ├── OutboxProcessor.start() ← background loops begin here ├── other processors + consumers ├── route discovery & mounting └── error handler (must be last) 7. Listen on the port 8. SIGINT / SIGTERM → graceful shutdown

Two things worth noticing as a beginner.

Config is validated before anything else runs. If a required environment variable is missing, the app refuses to start and prints exactly which one. That is far better than starting successfully and failing mysteriously an hour later. This is a pattern worth copying in your own work: fail fast, at boot, with a clear message.

Infrastructure is optional and gated. Each block checks IS_ENABLED first. That's what lets unit tests run with no database and no queue.

Graceful shutdown matters. When the process is asked to stop, it finishes in-flight requests instead of dropping them. Without this, every deployment would produce a handful of mysterious errors.

13. Decorators, or: where are the routes?

If you come from tutorials, you expect a file listing every route:

app.get('/users', getUsers);
app.post('/users', createUser);

There is no such file here, and its absence confuses everyone at first. Instead this project uses decorators — the @Something annotations above classes and methods.

A decorator is just a function that runs when the class is defined and can record information about it. This project uses them to build a registry at startup:

@Controller()                                   // ← "remember this class"
@injectable()
export class SubmissionFraudChecksController extends BaseController {

    @Get('/:submission_id/files/:submission_file_id/fraud-check')   // ← "this method is a route"
    @RateLimited({ max: 30, windowMs: 1000 })                       // ← "cap it at 30/sec"
    @AdminAuthUserMiddlewareWithProfile                             // ← "require a logged-in admin"
    async getFraudCheckState(req: Request, res: Response) { ... }
}

At boot, the startup managers walk the registry and mount everything. The flow is:

  1. Decorators record classes into DIRegistry, keyed by symbols (CONTROLLER, SERVICE, REPO, API, …).
  2. Registration functions ask the container to build each one.
  3. StartupRoutesManager reads the route metadata and calls Express for you.

The decorators you'll use most:

DecoratorPurpose
@Controller()Register a class as an HTTP controller
@Api()Group controllers under a base path like v1/programs
@Service()Register a business-logic class
@Repo()Register a data-access class
@Get/@Post/@Patch/@Put/@Delete('path')Declare a route
@RateLimited({ max, windowMs })Throttle a route
@AdminAuthUserMiddlewareRequire authentication
@EventConsumer({...}) / @EventHandlerBind a class to a queue
Practical consequence: to add an endpoint you add a method with a decorator. You never edit a central routes file — there isn't one. To find which code serves a URL, grep for a distinctive part of the path.

14. Following one real request

Here is a real endpoint from this codebase, traced all the way down. This is the single most useful exercise for understanding the project — do it yourself with a different endpoint afterwards.

Request: GET /v1/submissions/{sid}/files/{fid}/fraud-check

① Express receives the request ↓ ② Global middleware: helmet, cors, compression, cookie/body parsing, correlation id, response helpers (res.respond.*) ↓ ③ @RateLimited — Redis counter for this caller. Over budget → 429, stop. ↓ ④ @AdminAuthUserMiddlewareWithProfile — verify the JWT. Invalid → 401, stop. Valid → attaches req.auth_user ↓ ⑤ SubmissionFraudChecksController.getFraudCheckState • resolveScope(): does this file belong to this submission, in an org this user may see? No → 404 ↓ ⑥ FraudCheckService.evaluateGate(fileId, reviewerId) ← BUSINESS LOGIC • read the file • no fraud_verdict? → { not_applicable, no_verdict } • program gate disabled? → { not_applicable, program_disabled } • no live check row? → { required, verdict } • row has an outcome? → { satisfied, check, verdict } • otherwise → { in_progress, check, heldByYou } ↓ ⑦ Repositories run the actual SQL via Drizzle ↓ ⑧ res.respond.success('Fraud check state retrieved', state) → 200 + JSON

Notice what each layer did not do. The controller made no decisions about fraud. The service never touched req or a status code. The repository had no opinion about gates. That separation is the whole point, and it's why the same evaluateGate can be reused by a completely different controller (SubmissionReviewsController) without duplicating a line.

The response helper

You'll see res.respond.success(...), res.respond.notFound(...), res.respond.conflict(...) everywhere. These are added by middleware and exist so every endpoint returns the same envelope shape. Use them; don't hand-roll res.status(200).json(...).

Part 3 — The data layer

15. Schema and migrations

Each file in src/db/schema/ defines one table in TypeScript:

export const programSettings = pgTable('program_settings', {
    id: uuid('id').primaryKey().defaultRandom(),
    program_id: uuid('program_id').references(() => programs.id, { onDelete: 'cascade' }),
    min_reviews_required: integer('min_reviews_required').notNull(),
    fraud_check_required: boolean('fraud_check_required').notNull().default(false),
    created_at: timestamp('created_at', { withTimezone: true }).notNull().defaultNow(),
    deleted_at: timestamp('deleted_at', { withTimezone: true })
});

Things to note:

  • .notNull() — the column can never be empty. Prefer this. "Nullable by default" is how you end up with defensive if (x == null) checks scattered through the codebase.
  • .default(false) — existing rows get this value when the column is added, which is why adding a boolean flag doesn't break the 86,000 rows already there.
  • withTimezone: true — always store timestamps with a timezone. The app forces UTC (process.env.TZ = 'Etc/Universal' at the top of app.ts).
  • deleted_at — this is a soft delete. Rows aren't removed; they're marked. Queries filter them out. This preserves history and makes accidental deletion recoverable.
  • jsonb — a column holding arbitrary JSON. Flexible, but the database can't validate its shape, so you must be defensive when reading it. submission_files.metadata is jsonb, which is why the code writes (file?.metadata as Record<string, any> | null)?.fraud_verdict.

Migrations

Changing the TypeScript schema does not change the live database. A migration is a versioned SQL script that does. The workflow:

npm run db:generate     # compare schema to DB, write a migration file
npm run db:migrate      # apply pending migrations

Migration files live in drizzle/ and are committed to git. They run in order, so every environment reaches the same state.

Golden rule: never edit a migration that has already run anywhere. Write a new one. An edited migration will not re-run on machines that already applied it, so environments silently diverge — the worst class of bug, because everything looks fine locally.

16. Repositories

A repository wraps all access to one table. Business code never writes SQL directly; it calls a repo method.

Repos here extend BaseModelRepo, which provides a lot for free:

  • Standard CRUD — findFirst, findAll, insertOne, updateOneById, deleteOneById.
  • Pagination — findAll returns a paginated envelope, not an unbounded list. (Returning "all rows" is a production outage waiting to happen.)
  • Caching — optional cache-aside with automatic invalidation.
  • Audit logging — who changed what, when.
  • Atomic operations — race-free updates like atomicIncrement and atomicCompareAndSwap.
  • Relations — withRelations pulls related rows in one query.

Two ways to read, and why it matters

This distinction caused real confusion recently, so it's worth spelling out.

Relation-based reads (findFirst with withRelations) return whole rows. Everything on the table comes back. That's why GET /v1/programs/:pid/submissions/:sid returns each file's full metadata including fraud_verdict — nobody chose to expose it; nobody excluded it either.

Hand-written SQL (used for list endpoints, for performance) selects named columns via json_build_object(...). Only listed columns come back. That's why the submissions list has no metadata — the projection doesn't include it.

The lesson: before assuming a field isn't available, check which read path you're looking at. Two endpoints over the same table can expose very different amounts of it.

17. Transactions in practice

The pattern used throughout:

await this.transactionService.executeInTransaction(async (tx) => {
    const row   = await this.someRepo.insert(data, tx);
    const other = await this.otherRepo.update(row.id, patch, tx);
    await this.eventPublisher.publishInTransaction(event, tx);
    return other;
});

Three rules to internalise:

  1. Pass tx to everything inside. A repo call that forgets it runs outside the transaction and will not roll back. This is a silent bug — everything looks fine until a failure leaves half-written state.
  2. Keep transactions short. An open transaction holds locks. Never make an HTTP call to an external service inside one.
  3. Let errors propagate. Rollback happens by throwing. Swallowing an exception inside a transaction commits the partial work.
A real Postgres trap documented in this codebase. Inside a transaction, a raised unique-constraint violation aborts the entire transaction — every later statement fails too, and catching the error in JavaScript does not un-abort it. That's why inserts that expect contention use .onConflictDoNothing() and check the result, rather than try/catch. See the comment in SubmissionFileFraudCheckRepo.claim: this exact mistake once turned a clean 409 into a 500.

Part 4 — The event system

18. Why events exist here

When a file arrives from the external Vault service, several things must happen: compute a fraud verdict, run security-flag detectors, maybe fire a customer webhook. Doing all of it inside the upload request would be slow and fragile — one slow analyser would break uploads.

Instead the upload publishes one event and returns. Independent workers pick it up. If the fraud worker is down, uploads still succeed and the work is retried later.

19. The outbox pattern

This is the most important pattern in the project's event system, and it solves a problem that isn't obvious until you've been burned by it.

The problem. You save a submission to the database, then publish an event to RabbitMQ. Two separate systems. If the process crashes between them, the data is saved but the event never fires — permanently. Nothing retries, because nothing knows it was supposed to happen. Reverse the order and you get the opposite bug: an event fires for data that was never saved.

The solution. Don't publish to RabbitMQ at all. Write the event into the database, in the same transaction as your data. A separate background process reads that table and publishes.

Service code │ ▼ publishInTransaction(event, tx) │ ▼ outbox_events table ← INSERT, same transaction as the business data │ (both commit, or neither does) ▼ OutboxProcessor ← background loop, polls every 5s │ ORDER BY priority ASC, created_at ASC │ FOR UPDATE SKIP LOCKED ← safe with many app instances ▼ RabbitMQ (domain.events.topic) │ ▼ Consumers

Now the guarantee is airtight: if the transaction committed, the event exists and will eventually be published. If it rolled back, the event row rolled back too — no orphan messages.

FOR UPDATE SKIP LOCKED is the bit that makes it safe to run several copies of the app: each processor claims rows nobody else holds, skipping locked ones instead of waiting.

Publishing also supports priority and delayed delivery (availableAt) — which is how a claim schedules its own expiry five minutes in the future. From FraudCheckService.scheduleClaimTimeout, with the comment "Written in the same transaction as the claim via the outbox, so 'claimed but never released' is not a reachable state."

20. Consumers and workers

A consumer binds a class to a queue with a decorator:

@EventConsumer({
    events: [EVENT_TYPES.SUBMISSION_FILE_DATA_SYNCED],
    queue: QUEUE_NAMES.FRAUD_VERDICT_WORKER,
    exchange: 'domain.events.topic',
    config: { prefetch: 10, retryAttempts: 3, deadLetterQueue: true, timeout: 30000 }
})
export class FraudVerdictWorkerConsumer extends BaseMonitoredConsumer { ... }
OptionMeaning
prefetchHow many messages this worker holds at once. Higher = more throughput, more memory.
retryAttemptsHow many times to retry before giving up.
deadLetterQueueAfter final failure, park the message in the DLQ rather than dropping it.
timeoutKill a handler that hangs.

The dead letter queue is where messages go to be inspected and replayed after a bug is fixed — a message that fails forever must not block the queue behind it, and must not vanish silently. See docs/event-system/dead-letter-queue-implementation.md.

The eight workers currently running are in src/services/eventConsumers/workers/: vault file events, fraud verdict, security flags, callback triggers, submission notifications, location creation, and two timeout workers (review session, fraud check claim).

24. The review system

The normal path for a file:

File arrives (pending) ↓ Reviewer starts a review session ← claims the file, has a timeout ↓ Reviewer submits a decision ← approve / reject / request revision / hold ↓ with reason codes and notes as configured Has it met min_reviews_required? ├── no → wait for more reviewers └── yes → do the reviewers agree? ├── yes → auto-finalize (if settings allow) └── no → needs_final_review = true → adjudication ↓ File status set → submission status re-evaluated → callbacks fire

Program settings that shape this: min_reviews_required, max_concurrent_reviews_per_file, review_session_timeout_minutes, final_review_required_valid_entry, allow_direct_approval, require_reason_codes_for_decisions, require_notes_for_decisions.

25. The fraud subsystem

This is the newest and most intricate area, and the names are easy to confuse. There are three different things:

ThingWhere it livesWhat it is
Fraud verdictsubmission_files.metadata.fraud_verdictOur computed opinion. Written by FraudVerdictWorkerConsumer from Vault's raw signals. Has a tier: clear / review / high_risk.
Security flagssubmission_files.metadata.security_flagsCross-submission detectors — impossible travel, repeat capture, store distance. Separate worker, heavier compute.
Fraud checksubmission_file_fraud_checks tableA human attestation: a reviewer looked at the evidence and made a call. Outcome is verified or fraud_detected.

The verdict is a machine opinion; the check is a person's signature. Keeping them apart is deliberate.

Why fraud checks aren't just reviews

A fraud check reads like a review, so why a separate table? The schema comment answers it directly: a reviews row would count toward min_reviews_required, feed the conflict engine, move completed_review_count, and consume concurrency slots — all in the code path that decides whether submissions auto-finalize, "where a miss is silent and serious."

A good lesson in system design generally: two things that look alike are still different if they participate in different rules.

The gate

When a program sets fraud_check_required = true, a file carrying a verdict must be fraud-checked before it can be reviewed. FraudCheckService.evaluateGate returns one of five states, and the two entry points into review refuse to proceed on required or in_progress.

Two design choices worth studying:

  • The gate fails open. If the settings lookup errors, it treats the gate as disabled. The comment explains the trade: "a missed fraud check, not a stuck queue." Deciding which way a failure should fall is a judgement you'll face often.
  • The row is the claim. Opening the page inserts a row with outcome IS NULL; deciding fills the same row in. No separate claim table, no second write path.

27. Testing

Two kinds, and knowing which to write is a skill in itself.

Unit tests

__tests__/unit/ — test one class with everything else faked. No database, no network, milliseconds to run.

mockProgramSettingRepo.getOne.mockResolvedValue({ fraud_check_required: false });

const state = await service.evaluateGate('file-1', REVIEWER_A);

expect(state).toEqual({ gate: 'not_applicable', reason: 'program_disabled', verdict });

This is dependency injection paying off. The service asked for a repo; the test handed it a fake.

Use unit tests for logic with many branches — every state a function can return, every edge case.

Integration tests

__tests__/integration/ — start the real app against a real database and make real HTTP calls with supertest.

const response = await reviewer.get(fraudCheckPath(ids));

expect(response.status).toBe(200);
expect(response.body).toMatchObject({ gate: 'not_applicable', reason: 'program_disabled' });

Use integration tests for wiring — that the route is mounted, auth applies, the query is valid SQL, the response shape is right. A unit test cannot catch a typo in a route path.

toMatchObject vs toEqual. toEqual demands an exact match; toMatchObject checks the listed fields are present and ignores extras. Integration tests here use toMatchObject deliberately, so adding an optional field to a response doesn't break unrelated tests — the same additive-change principle from §3.

28. Adding a feature, end to end

A checklist, in the order that avoids rework:

  1. Understand the existing flow first. Find the nearest similar endpoint and trace it as in §14. Most features are a variation on something already here.
  2. Decide the layer. New table? New rule? New endpoint? Often only one layer changes.
  3. Schema, if needed. Edit src/db/schema/, run db:generate, review the generated SQL, run db:migrate. New columns should be nullable or have a default so existing rows stay valid.
  4. Model. Add or update the Zod schema in src/models/ — this is where untrusted input is checked.
  5. Repository. Add query methods. No business rules here.
  6. Service. The actual logic. Own the transaction. Publish events inside it.
  7. Controller. Parse input, call the service, map results to status codes. Add @RateLimited and an auth decorator.
  8. Tests. Unit tests for the branches, one integration test for the wiring.
  9. Check the whole surface. Does a list endpoint need the new field? A callback? Does an existing consumer need updating?
  10. Run type-check, lint, and both test suites before opening a PR.
Ask this before writing any code: can two users do this at the same time? If yes, you need a database-level guarantee (unique index, atomic operation, FOR UPDATE), not just an if statement. Nearly every hard bug in a system like this is a race condition.

30. Conventions this codebase holds to

These aren't arbitrary style rules; each exists because breaking it caused a real problem.

  1. Comments explain why, not what. The code says what it does. Comments here record the decision and, often, the bug that motivated it. When you change such code, update the comment — and if you're about to remove a guard, read its comment first; it usually explains what broke last time.
  2. One producer per contract. If two endpoints return the same shape, they call the same method. Hand-building a second version of a payload has already caused a bug here.
  3. Enforce server-side, don't just signal. Anything a client could route around must be checked on the server.
  4. Fail fast at boot, fail open at runtime — where failing closed would block users from work they can't unblock. Decide consciously and write down which you chose.
  5. Invariants belong in the database. "This can only happen once" is a constraint, not an if.
  6. Additive API changes only, unless you're versioning.
  7. Never edit an applied migration.
  8. Pass tx everywhere inside a transaction.
  9. Consumers must be idempotent.
  10. Paginate every list.
